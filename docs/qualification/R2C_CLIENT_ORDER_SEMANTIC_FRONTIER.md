# R2C — official 26.2 receiving-client ordering and branch-shape review

**Status: source-free JVM method review candidate; no VAR/SEM admission.**
This review follows the official Mojang client artifact and the
receiving-client call graph already established in PRs #331–#338.
The official artifact is checked against Mojang's exact 26.2 SHA-1/size,

## Exact bounded method roots

The new `tools/r2c_client_order_semantic_frontier.py` inspects exactly
seven methods, with no broad discovery of unrelated classes:

1. `RegistryDataCollector$ContentsCollector.append`: accumulated entry
   lists use `Map.computeIfAbsent` then `List.addAll`.
2. `NetworkRegistryLoadTask.load`: receives `NetworkedRegistryData.elements`,
   calls `List.iterator`, appends decoding futures to a list, calls
   `net.minecraft.util.Util.sequence`, and attaches
   `CompletableFuture.thenAcceptAsync`.
3. `NetworkRegistryLoadTask.lambda$load$2`: constructs a
   `List.stream`, invokes `registerElements`, and registers tags.
4. `net.minecraft.util.Util.sequence`: distinguishes empty and nonempty
   lists, checks input size, and in the multiple-future case invokes
   `CompletableFuture.allOf` and `thenApply`.
5. `Util.lambda$sequence$0`: calls `List.stream`, `Stream.map`
   (independently bootstrap-bound to `CompletableFuture.join` in #338),
   and `Stream.toList`.
6. `RegistryLoadTask.registerElements`: invokes `Stream.forEach`.
7. `MappedRegistry.register`: contains the dense-ID operations
   `ObjectList.size`, `ObjectList.add`, and `Reference2IntMap.put`.

Every call-order witness must be present in its *own named method*, and
must appear in the expected relative order. The probe fingerprints the
exact selected declaration and **all parsed instruction rows**, not only
a subset of invoked methods, and records every explicit conditional jump
edge and the return/throw offsets. All instruction and branch counts are
bounded; truncated, malformed, ambiguous, missing or reordered evidence
fails closed. No classfile, source, disassembly or full instruction listing
is committed or archived. The short-lived CI artifact contains only
fingerprints, branch offsets, and concise symbolic call checkpoints.

## Independent JDK 25 sequencing and exceptional-completion oracle

standard-library oracle**, not copied Minecraft client source. It checks

`allOf(...).thenApply(...)` / `List.stream().map(join).toList()` and

both arms of conditional jumps, and straight-line successors. It accepts

## Client sequence branch-operand provenance (source-free JVM evidence)

The existing bounded `Util.sequence` official-client probe additionally
checks the **immediately adjacent operand producers** at both conditional
jumps, not just their names or control-flow destinations. It requires:

- `aload_0` followed by `invokeinterface List.isEmpty:()Z`, then
  `ifeq` at bytecode offset 6. According to JVM `ifeq` semantics,
  false jumps to offset 16; true falls through to the empty-path
  return at offset 15.
- `aload_0` followed by `invokeinterface List.size:()I`, then
  `iconst_1` and `if_icmpne` at offset 23. A size unequal to one
  jumps to offset 44; equality falls through to the singleton path.

The official 26.2 client CI pins the exact producer offsets
(`isEmpty` at 1, `size` at 17), opcodes, method descriptors,
comparison constant, branch polarity and return offsets. The report
exports only this concise source-free operand witness. Regression tests
modify the receiver local, invoked method descriptor, comparison
constant and conditional opcode while preserving the earlier ordered
calls and normal CFG: each must fail closed.

**Scope of this evidence:** both immediate branch conditions are now
locally tied to the receiver list and JVM predicates. This is a
specific, reviewable slice of operand dataflow, not full operand-stack
interpretation of every instruction, not a proof that the input list
originates unchanged from the Configuration payload, and not a proof
that any CompletableFuture callback runs or registers entries in order.
In particular, exception tables, async scheduling, registration
duplicate/error handling, known-pack selection and **independent
VAR/SEM source admission** remain open. Never set any authority flag
based on this operand witness.

## All explicit `MappedRegistry.register` exit paths (new bounded review)

The existing pinned actual-client JVM probe also classifies **every
reachable normal return and explicit `athrow`** in the exact
`MappedRegistry.register` method. Rather than concluding correctness
from the existence of one path, it follows all five observed conditional
and goto branches, with a finite acyclic exploration bound. Each path
records its terminal bytecode offset/opcode and whether it passed the
previously pinned dense-ID checkpoints `ObjectList.size`,
`ObjectList.add`, and `Reference2IntMap.put`.

The independently pinned 26.2 client workflow requires early
`athrow` exits at bytecode offsets **53, 89, 137**, before any of those

has passed *all three in order*. Mutation tests require a premature
normal return and a late explicit throw to be rejected. No official
source or disassembly is committed; the exported source-free result
contains only exit classification and checkpoint symbols.

**Precise limitation:** This is a control-flow property for **explicit
JVM exits**. Any invoked method may itself throw, including after
partial mutation; no rollback guarantee or duplicate-key/value policy
is inferred here. The branch guard operands, exact mutation effects,
registerElements stream traversal, executor error propagation, known-pack
identity, and independent source VAR/SEM remain **unreviewed/unadmitted**.
The result cannot authorize production biome ordinals.

## Bounded registration exception-handler source-free frontier

The existing exact official-client 26.2 `javap -c -p` reviewer now
parses the **JVM `Exception table`** for the already-rooted
`RegistryLoadTask.registerElements` method. It validates the
`from`, exclusive `to`, handler target and caught exception class
against actual instruction offsets; malformed, ambiguous, missing or
unbounded tables fail closed. The emitted source-free record also
identifies the exact `Stream.forEach` call offset and whether an
exception-table range covers that *direct invocation*.

This is not the same as complete exceptional execution semantics.
The table's protection range can include more than one invoked method,
and a caught throwable can originate from downstream code. Nor does
the presence of a handler prove rollback of earlier inserted IDs.
An exception may leave a partially populated receiving-client registry.
The separate `MappedRegistry.register` explicit-exit witness proved
in #406 does not exclude exceptions thrown by its invoked delegates.
All independent source VAR/SEM and production flags remain false.

The existing CI runs this against the actual SHA-1/size-checked client,
prints only finite handler metadata and separately asserts that the
`rollback_or_partial_mutation_semantics_proven` field stays false.
No official Mojang class text, source listing or disassembly is shipped.

## Interpret the evidence carefully

Structural call ordering is **necessary but not sufficient** to establish
the numeric client biome ID law. In particular:

- Branch reachability, loop dataflow, exception tables and all JVM stack
  transitions must be reviewed to prove the incoming list is consumed
  once, without reordering or omissions.
- The empty/singleton/multiple-future cases of `Util.sequence`,
  exceptional completion of `allOf`, and `join` error propagation
  must be checked independently.
- The callback confirmed in PR #338 must be shown to receive the ordered
  sequence result and to register entries in that order. `Stream.forEach`
  and `List.stream` are evidence, but not by themselves complete
  registration correctness.
- Verify duplicate key/value behavior and potential partially populated
  registry on exceptional registration.
- Confirm the actual selected known-pack set and receiving-client biome
  registry are identical to the Configuration publication and the chunk
  palette's ID source.
- Pin VAR and SEM findings against exact independently reviewed source
  artifacts, and satisfy Helve's independent gate before enabling live
  chunk publication.
